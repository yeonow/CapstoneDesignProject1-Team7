### 위치를 상태에 넣을지

이것이 가장 큰 설계 차이다. 시뮬레이션에서는 탐색 장치의 좌표를 쉽게 알 수 있지만, **실제 실험에서 알고리즘에 좌표를 주지 않는다면** 좌표를 사용해 학습한 정책을 그대로 옮기기 어렵다. 따라서 1차 상태는 다음처럼 맞추는 편이 일관된다.

```text
상태 = (현재 RSSI 수준, 최근 RSSI 변화, 직전 이동 방향)
```

반대로 실제 장치의 위치를 계속 기록해 알고리즘에도 제공할 계획이라면 좌표를 넣는 실험도 가능하다. 팀에서 **실제 운용 중 어떤 정보를 얻을 수 있는지** 먼저 확정해야 한다.

### 4방향과 8방향

8방향은 대각선 길을 허용하지만, 첫 구현에서 꼭 필요한 것은 아니다. 우선 4방향으로 측정·이동·학습 과정이 제대로 연결되는지 확인한다. 8방향을 비교할 때는 대각선 한 칸의 실제 이동 거리가 직선 한 칸보다 길다는 점을 반영한다.

### 목표에 도착했다는 판단

시뮬레이션은 목표의 실제 위치를 아니까 **정말 도착했는지** 평가할 수 있다. 실제 탐색은 목표 위치를 미리 모르므로 RSSI가 여러 번 강하게 잡힌 곳을 **위치 후보**로 표시한다. 강한 RSSI 한 번을 실제 발견으로 처리하면 잘못된 위치를 찾은 경우를 놓칠 수 있다.

## 1차 구현 권장안

1. **목표:** 미리 지정한 스마트폰 Wi-Fi Hotspot의 신호원을 찾는다.
2. **장비:** 시뮬레이션에서 학습한 뒤, Raspberry Pi를 사람이 옮기며 실제 RSSI로 검증한다.
3. **상태:** RSSI 수준 + 최근 변화 + 직전 이동 방향. RSSI 기준값은 실측 자료를 보고 정한다.
4. **행동:** 상·하·좌·우. 첫 이동도 같은 행동 선택 규칙을 따른다.
5. **보상:** RSSI가 강해지면 긍정, 약해지면 부정. 이동 비용과 재방문 점수는 다음 실험에서 하나씩 추가한다.
6. **비교:** 같은 시작점·목표·신호 조건에서 Greedy RSSI, Q-learning, 가능하면 Random을 시험한다.
7. **평가:** 성공률, 잘못된 위치 후보 수, 이동 횟수·거리, 탐색 시간, 잡음이 늘었을 때의 변화를 함께 기록한다.

## 구현 전에 팀이 맞춰야 할 것

- 실제 실험에서 **좌표를 알고리즘에 제공할지** 결정한다.
- 시뮬레이터와 Q-learning 코드가 같은 **상태 형식·행동 번호·보상·종료 조건**을 사용하도록 정한다.
- 실제 RSSI 측정값으로 **RSSI 수준과 변화 판단 기준**을 정한다.
- 시뮬레이션의 **실제 목표 도착**과 현장의 **위치 후보 판정**을 따로 정의한다.

> DQN·PPO·belief map, 여러 종류의 목표 신호 구분은 1차 구현이 끝난 뒤 필요성이 확인되면 검토한다. 이 방법들이 Q-learning보다 좋은지는 같은 조건의 실험 결과로 판단한다.
